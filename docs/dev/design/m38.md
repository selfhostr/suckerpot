# M38: better abuse reports

Status: approved for v0.14 (2026-11-22), not implemented yet. The owner's decisions are in section 10.

## 1. Problem and goals

A node can find abuse contacts, build reports, send them through the VPN, read the replies and follow the reported targets (M22, M25, M26, M27). Four things are still missing:

- We cannot say whether reports help. The Results page counts replies and takedowns of payload URLs. For an attacking address it only says "Quiet" or "Active", with nothing to compare against.
- The machine-readable part is old and often missing. Only one-source reports carry X-ARF, and in the 2010-era v0.2 format.
- A busy provider gets many mails a day. Each kind of report goes on its own, and a new draft goes out about an hour after the previous one.
- Desks that only take a web form are skipped, and then nothing happens. The owner has to do all the work by hand.

Goals (all approved by the owner for v0.14):

- G1. **Measure the effect of reports.** Compare reported sources with similar sources that were not reported, and say honestly whether reported ones stop attacking more often. Show nothing until there is enough data. The hub does the same across the network, within the M34 anonymity rules.
- G2. **X-ARF on every mail.** Each abuse mail carries one machine-readable report per source, in the current X-ARF version, next to the human text and the CSV.
- G3. **One mail per provider per day.** All the sources that share an abuse recipient go into one daily digest.
- G4. **A form queue.** A "To submit by form" queue with a copy kit, a weekly grouping per provider, a "Submitted" button, and a shared, reviewed directory of known abuse forms that ships with releases.

Non-goals:

- N1. No automatic form submission. Captchas, terms of service and credibility all forbid it.
- N2. No new contact with an attacker. Measuring uses our own sightings only, as the takedown tracker does. We never probe an address to see whether it is still up.
- N3. No mail to anyone the owner did not choose. X-ARF goes to the same abuse recipient as the human text. Nothing is copied to a third party such as a reporting platform.
- N4. No claim of cause. The measure compares two groups. It does not prove that a report caused a takedown, and the page says so.

## 3. G1: measure the effect of reports

### 3.1 The question

"When we report an attacking address, is it less often still attacking a week later than a similar address we did not report?"

Only attack sources (IP addresses) are measured. Payload URLs already have takedown statistics (M27). C2 servers are never contacted, so we cannot see them stop.

### 3.2 Method

**Units.** One reported source is an address that was a subject of a sent report of kind `attack_source` (sent by SMTP, marked sent by hand, or submitted by form, section 6). Its **index time** `T0` is the send time of its first report in the period. Demo reports never count.

**Controls.** A control is an address that passed the same candidate rules (section 2) in the same days, but was not reported. On a node that reports everything, controls exist only where something stopped the report: no contact found, a muted recipient, a form-only desk not yet submitted, a dead address, the daily cap, a draft the owner discarded or never sent. Addresses on the never list or in the self terms are never controls (they are not attackers we would report). Addresses that the network reported in the 30 days before `T0` or during the follow-up are left out of both groups, because the hub's report would mix up the result.

**Matching.** Each reported source gets at most one control, chosen without replacement. The control gets the same index time `T0`. A control must:

1. have been a candidate within 3 days of the moment the reported source became a candidate;
2. not have been reported by this node before `T0 + N + 7 days` (if it is reported later, the pair is dropped, not counted as a success);
3. match exactly on the **activity class** over the 7 days before `T0`: login only; login then commands; download; exploit (a severe tag);
4. match exactly on the **volume bucket** of events in those 7 days: 1 to 9, 10 to 99, 100 to 999, 1,000 or more;
5. match exactly on **recency**: last seen 0 days, 1 to 2 days, or 3 to 7 days before `T0`.

Then the closest provider wins, in tiers:

| Tier | Provider match |
| --- | --- |
| A | Same ASN |
| B | Same provider size class and same country |
| C | Same provider size class |

There is no outside list of ASN sizes, so the **provider size class** is built from what we have: the RDAP block size of the address (`/24` or smaller, `/23` to `/16`, larger than `/16`; for IPv6 `/48` or smaller, `/47` to `/32`, larger) and the number of distinct addresses of that ASN we saw in the last 30 days (1, 2 to 9, 10 to 99, 100 or more). The class is the pair. A reported source with no control in any tier is **unmatched**. It is counted and shown, never used.

**Outcome.** "Still seen attacking at N days" means at least one session from the address on any of our sensors during the 7 days from `T0 + N` to `T0 + N + 7`. The primary horizon is **N = 7** (the same 7 days as the takedown "Quiet" state). A second horizon, **N = 30**, is shown when it has enough data. Any session counts, not only reportable activity: an address that only scans is still active.

**Observation check.** A pair counts at a horizon only when its window is over and our sensors were up: at least 6 of the 7 days of the window have sessions from at least 10 distinct addresses on this node. Otherwise the pair is "not observed" for that horizon and left out (a node that was down for a week must not look like a week with no attacker).

**Statistics.** For the `n` observed pairs at a horizon:

- `a` both seen, `b` only the reported one seen, `c` only the control seen, `d` neither.
- Share still seen: reported `(a + b) / n`, control `(a + c) / n`. Difference `(b - c) / n`.
- A 95 % interval for the paired difference by Newcombe's method 10 (Wilson score based). It behaves well with small counts and never leaves -1 to 1.

**Minimum before a number is shown.** At least **30 observed pairs** and at least **10 discordant pairs** (`b + c`). Below that, only the progress is shown. The interval is wide at first. With about half the pairs discordant, the half-width is roughly 1.4 / sqrt(n):

| Pairs | Half-width of the 95 % interval |
| --- | --- |
| 30 | about 25 points |
| 100 | about 14 points |
| 300 | about 8 points |

So a small node will at best see "a clear difference" for a large effect. That is the honest answer.

**Optional holdout (decision D9).** Without randomness, a control was not reported for a reason, and that reason may also explain its future (a provider with no abuse contact may also never clean anything). A true test needs a random holdout: with `ABUSE_EFFECT_HOLDOUT_PCT` (0 by default, at most 10), that share of new candidates is chosen at random and not reported for 21 days, then reported as usual if still active. Held-out sources become the preferred controls (tier H, shown apart). The owner must turn this on knowingly: it delays some reports.

### 3.3 Confidence wording

Three verdicts, chosen only from the interval:

| Verdict | When | Sentence (example numbers) |
| --- | --- | --- |
| `not_enough_data` | Below the minimum | "Not enough data yet to tell whether reports help: 12 of 30 comparable pairs." |
| `lower` | The whole interval is below 0 | "Reported sources were less often seen attacking a week later: 38 % against 61 % for similar sources that were not reported (84 pairs; the difference is between 9 and 37 points). This compares two groups; it does not prove the reports caused it." |
| `no_clear_difference` | The interval contains 0 | "No clear difference yet: 52 % of reported sources and 55 % of similar unreported sources were still seen a week later (84 pairs). The gap could be chance." |
| `higher` | The whole interval is above 0 | "Reported sources were more often seen attacking a week later: 64 % against 41 % (84 pairs). This compares two groups; it does not say why." |

Rules: never "effective", "works" or "caused"; percentages are whole numbers; the pair count is always shown next to a percentage; the interval is given in points; a percentage never appears under the minimum.

### 3.4 Data model (node)

Migration (next free number), one table and one view:

| Table `report_effect_pairs` | Meaning |
| --- | --- |
| `id`, `created_at` | |
| `index_at` | `T0` |

Plus `report_effect_unmatched (index_at, value, reason)` for the count of unmatched sources, and, for the holdout, `abuse_holdouts (value, chosen_at, release_at)`. Frozen rows are never updated (a trigger, like the observatory). The ingest role owns the tables; the API role reads the summary view only, not the addresses.

### 3.5 Worker

`ingest/ingest/takedown/effect.py`, run once a day by the takedown worker (it reads the same sightings). Steps: make pairs for reports sent in the last 3 days (candidate sets are recomputed with the same SQL as `candidates.py`, as of a past time, from `sessions`); freeze the 7-day and 30-day outcomes whose window is over; clear old addresses. On first start it backfills pairs from the sent reports still inside the session retention, so a node that already reported for a few weeks gets results soon. Bounded: at most 500 new pairs and 2,000 outcome checks per run, indexed reads only (`ix_sessions_src_ip`). No network access at all: it does not need the egress gate.

### 3.6 UI and status

**Results page.** A new card, **Do reports make a difference?**, after "Did anyone answer?". It opens with the verdict sentence. Under the minimum it shows a meter ("12 of 30 pairs") and nothing else. Above it: two bars (reported, similar not reported) with the share still seen at 7 days, the interval as text, and a 30-day row when that horizon has enough data. A "How this is measured" disclosure lists the tiers used, the unmatched count, the pairs left out (not observed, control reported later, network reported), and whether a holdout is on. The period filter applies to `T0`. Colours: neutral tones only, never red or green (it is not a score).

**`just status`.** One line in the Reports section: `Report effect: not enough data yet (12 of 30 pairs)`, or `Report effect: 38% of reported vs 61% of similar sources still active after 7 days (84 pairs, clear difference)`. Never a warning: it is information. The JSON form gets `report_effect {verdict, pairs, needed, seen_reported, seen_control, lo, hi}`.

**API.** `GET /api/v1/results/effect?since=&until=&horizon=7|30` returns the summary only (no address).

### 3.7 The network measure (hub)

**H1, in v0.14: the hub's own reports.** The hub already knows which addresses it reported and which confirmed, reportable addresses it did not report (desk paced, daily cap, cancelled, still waiting for review after 7 days). It also already receives, from eligible nodes, a daily observation per address. So it can run the same method with no new data from nodes:

- unit: an address the hub reported; control: a confirmed, reportable address not reported, matched on activity, login bucket, number of reporting nodes (5 to 9, 10 to 24, 25 or more) and ASN tier;
- outcome: observed by at least one eligible node during days 7 to 13 after `T0`;
- observation check: every day of the window is a `standard` observatory day (at least 3 eligible nodes reported attacking addresses);
- computed before the 14-day observation purge, frozen once per pair.

Published in `network.json` as an additive section `report_effect`: one entry per complete month of `T0`, `{month, pairs, seen_reported_pct, seen_control_pct, lo, hi, verdict}`. M34 rules apply: only eligible nodes count; frozen once; `pairs` rounded to tens; shares and bounds in whole points; at least 50 pairs per month, else `not_enough_data` with no numbers; only when `outcome_precision` is `exact`, `suppressed` otherwise (rule 10). The anonymity test walks the new section. Nothing per node is involved: the outcome is "some eligible node saw it", never which one.

**H2, later and opt-in (decision D10): node reports.** A node's own reports are not known to the hub. Pooling them would need each node to send its paired counts for each ISO week of `T0`: only `(n, b, c)`, after the week's 30-day outcomes are frozen, only for weeks with at least 10 pairs, rounded to the nearest 5. The hub would keep the per-node rows at most 14 days, sum them into a frozen weekly row only when at least 3 eligible nodes contributed, and publish under the same rules. Even rounded counts tell the hub how much a node reports, and a new message needs a hub release first. This is designed here but comes after v0.14 (decision D10), off by default (`NETWORK_SHARE_REPORT_EFFECT=false`).

### 3.8 Privacy and security

- No outbound traffic. The measure reads our own sessions.
- Addresses in `report_effect_pairs` are local and cleared after use. They never enter a report, a feed or the hub.
- The holdout only delays reports. It never sends one that would not have been sent.
- Wrong numbers are the main risk. The minimum, the observation check and the fixed wording are the defence. A test checks that no percentage is ever rendered under the minimum.

### 3.9 Tests

- Statistics: Newcombe interval against published reference values; verdict boundaries (interval touching 0 is `no_clear_difference`).
- Matching: exact strata respected; tier order; no control reused; a later-reported control drops the pair; network-reported addresses excluded; demo excluded.
- Observation check: a week with the node down gives `not observed`, not "not seen".
- Freeze: a frozen row cannot change (trigger test); addresses cleared on time.
- Backfill: bounded per run, idempotent.
- UI: under the minimum the card shows the meter and no percentage (component test); the wording contains no "effective" or "caused".
- Hub: Sybil nodes do not count; `report_effect` follows rule 10; anonymity walk; frozen months never change.

### 3.10 Acceptance criteria

- On the owner's node today the card and `just status` say "not enough data yet" with the pair count.
- With the integration fixture of 120 synthetic pairs, the card shows the right shares, interval and verdict, and the same numbers appear in `just status --json`.
- No address leaves the node because of this feature (egress test: no new destination).
- The hub publishes `report_effect` only with production thresholds and at least 50 pairs a month.

## 4. G2: X-ARF on every mail

### 4.1 Which version

The X-ARF v0.2 format we render (YAML in `report.txt`) is from about 2010. The format has since moved to **XARF v4**: JSON, kept by the XARF project at xarf.org with schemas in the `xarf/xarf-spec` repository (MIT licence). Version **4.2.0** was released on 2026-03-20 (checked on 2026-11-22). The older `abusix/xarf` repository (v3) is archived and points to v4. AWS Abuse Signal validates against the v4 schema and converts v3 on input; Abusix maps its API to XARF.

We move to v4 and stop rendering v0.2 (decision D1). The v4 schemas are vendored into the tests (MIT notice in `THIRD_PARTY_NOTICES.md`) so CI validates every rendered report offline.

### 4.2 The mail layout

XARF v4 over SMTP (the spec's "Email Transport" page) is an RFC 6522 report:

```
Content-Type: multipart/report; report-type=feedback-report
  1. text/plain                 the human text (ours, unchanged)
  2. message/feedback-report    Feedback-Type: xarf / User-Agent: <setting> / Version: 1
  3. application/json           xarf.json, base64, attachment
```

There is no `X-ARF` or `X-XARF` mail header in v4, so we drop ours. The spec covers one report per message and says nothing about several. A digest (section 5) holds many sources, so (decision D2):

- **One source:** exactly the spec layout above, plus `evidence.csv` as a fourth part.
- **Several sources:** `multipart/mixed` with the human text, `evidence.csv`, and one JSON file per source, `xarf-001.json` to `xarf-100.json`. Each file is a complete, valid v4 report. The summary in the text lists the file name next to each source.

This is a deviation for the many-source case. A desk whose parser takes only spec-shaped mails will skip it, and its staff still have the text and the CSV. If the form directory (section 6.5) says a desk parses XARF strictly, the owner can choose "one mail per source" for that recipient (`abuse_recipients.xarf_strict`), which sends spec-shaped mails, still counted against the daily cap one by one.

### 4.3 Field mapping

Required v4 fields: `xarf_version`, `report_id`, `timestamp`, `reporter`, `sender`, `source_identifier`, `category`, `type`.

| Field | Value |
| --- | --- |
| `xarf_version` | `"4.2.0"` |
| `report_id` | A fresh random UUID v4 per source per mail. Stored on the subject row (`abuse_report_subjects.xarf_id`), unrelated to every internal id |
| `timestamp`, `first_seen`, `last_seen` | First and last activity of the source in this mail, with the report's time precision (minute by default) |
| `reporter`, `sender` | Both the same: `contact` = the reply contact; `domain` = the domain of the reply contact; `org` = a new optional setting `xarf_org`, else the domain of the reply contact (decision D7). No shipped wording |
| `source_identifier` | The address, or the host of a payload URL |
| `source_port` | The source port of the first activity, when known (recommended by the spec for CGNAT) |
| `protocol` | `tcp` or `udp` |
| `destination_port` | The port that was attacked. **`destination_ip` is never set**: it is our own address |
| `tags` | Only from allow-lists: `service:<name>` (the protocol's `SERVICES`), `cve:cve-yyyy-nnnn` (only CVEs named by a signed trap pack or the CVE watch), `malware:<family>` (`FAMILIES_V1`). Never a trap pack id or local tag: those are in the public repository and would mark the sender as this project |
| `description` | A short factual sentence built from the same labels as the text ("152 login attempts on SSH, 2026-11-20 08:14 to 11:02 UTC"), at most 300 characters |
| `evidence` | One item: `content_type: text/csv`, the source's rows of `evidence.csv` (at most 50), base64, with `hash: sha256:<hex>` and `description: "Log lines (UTC)"` |
| `evidence_source`, `confidence` | Not set (decision D6). The spec's natural value would be `honeypot`, which tells the attacker's provider, and so maybe the attacker, what we are. Both fields are only recommended |

Category and type per kind of subject (the v4 type list was read from the 33 schema files in `xarf-spec/schemas/v4/types`):

| Our evidence | XARF v4 | Type-specific fields |
| --- | --- | --- |
| Attack source, only login attempts | `connection` / `login_attack` | `protocol`, `first_seen` (required), `destination_port`, `last_seen` |
| Attack source, a login then commands, or a download command | `connection` / `login_attack` | Same, plus tags such as `service:ssh`. The commands are in the evidence. A "compromised" type would describe the source host, which we cannot see |
| Attack source with an exploit (severe tag, CVE tag, `exploit_attempt` activity) | `connection` / `vulnerability_scan`, `scan_type: web_vuln_scan` (HTTP) or `mixed` | `protocol`, `first_seen` (required), `vulnerabilities_probed` (CVE ids), `total_requests`, `user_agent`. v4 has no "exploit attempt" type; this is the closest one that describes the sender's traffic |
| Attack source, SQL injection pattern (web flag `sqli`) | `connection` / `sql_injection` | `http_method`, `attempts_count`; `target_url` only as a path, never with our host name |
| Payload host (a URL or host that served a file) | `content` / `malware` | `url` (required, the URL that served the sample), `domain`, `file_hashes.sha256`, `malware_family`, `file_metadata.file_type` |
| Command server | `infrastructure` / `botnet` | `compromise_evidence` (required): "A malware sample (sha256 ...) uses this address as its command server." |

Several activity classes on one source: exploit wins over login, so one source is one report.

### 4.4 Data model

- `abuse_report_subjects.xarf_id uuid` (random, unique, set when a subject first goes into a mail) and `abuse_report_subjects.kind` (section 5.2).
- `report_settings.xarf_org text NULL` (at most 100 characters).
- `abuse_recipients.xarf_strict boolean NOT NULL DEFAULT false`.

### 4.5 Renderer and send path

- `reporting/suckerpot_reporting/xarf.py`: `render_xarf_v4(evidence, settings, subject) -> dict` (pure), `xarf_parts(...)` for the MIME parts. The v0.2 code and `XARF_SCHEMA_URL` go. `RenderedMessage.xarf: bool` becomes `layout: "plain" | "report" | "digest"`.
- `ingest/ingest/reportmail/outgoing.py` builds `multipart/report` or `multipart/mixed`. JSON parts are base64 as the spec asks; the rest stays 7bit ASCII.
- The report page's "X-ARF" tab lists one JSON per source, read-only, with copy and download buttons. The `.eml` download contains the same parts.

### 4.6 Privacy and security

What a desk receives in the JSON is the same set of facts as in the CSV and the text today: the source address and port, times, counts, attacked port and service, the redacted command lines and user agents, hashes and families, plus the reply contact and its domain. Nothing new about the node.

- **Never sent:** our address (`destination_ip`), host names, sensor names, trap pack ids, internal ids, `_internal`, `evidence_source: honeypot`.
- **The guard must see what is sent.** Two new views in `guard.artefact_strings`: base64 MIME parts are decoded (the `.eml` view already does this; it is extended to `application/json` parts), and every `evidence[].payload` in a JSON report is base64-decoded and scanned too. Without the second one, base64 would hide a leak from the guard. A test plants the self address in an evidence payload and expects `guard_failed`.
- **Schema check before send.** Each JSON is validated against the vendored schema in ingest; an invalid one blocks the send with `xarf_invalid` (a bug, never a silent fallback).
- **Fingerprinting.** Every node now sends the same JSON shape. That is true of any XARF sender, and the shape follows a public standard. The free-text fields (`org`, the human text) stay the owner's; the defaults are values the owner already sends (the reply contact domain, `Mozilla/5.0`).
- **Third parties.** None. XARF goes to the abuse recipient only. Platforms that parse XARF for a desk are the desk's own processors.

### 4.7 Tests

- Every mapping row: the rendered JSON validates against the vendored 4.2.0 schema (core plus type).
- `destination_ip` never present (property test over random evidence).
- Tags only from the allow-lists; a trap pack tag never appears.
- Guard: a leak in any field, in the evidence payload, or in the MIME-encoded part blocks the mail.
- MIME: one source gives `multipart/report` with three or four parts in order; several sources give one JSON per source; the text names each file.
- `report_id` is random, unique, stored, and not equal to `public_id`, `id_seed` or the reply token.

### 4.8 Acceptance criteria

- Every mail sent by a node carries one valid XARF v4 JSON per source.
- `just abuse-guard-check` covers the new parts and passes on the owner's node.
- The X-ARF tab and the `.eml` show exactly what SMTP sends (byte comparison in the integration test).
- The v0.2 renderer is gone from the node; the hub follows in P4.

## 5. G3: one mail per provider per day

### 5.1 Rules

- **Grouping key:** the effective recipient address (`COALESCE(override_mailbox, mailbox)`), across all kinds (decision D3). A digest has a section per kind: attack sources, payload hosts, command servers.
- **Per-source rules are unchanged:** the candidate rules, the 7-day look-back, the 30 min settle, the 14-day resend per source, the never list, the network dedupe and the identity guard.
- **One digest open per recipient.** It is rebuilt every hour, as drafts are today, and gains new sources until it is due.
- **Due time:** once a day at the node's **digest hour**. A new install picks a random minute between 06:00 and 09:00 UTC (decision D4), so nodes do not all send at the same minute. The owner can change it in Settings > Sending (shown in local time).
- **At most one digest per recipient per UTC day**, plus overflow parts: a digest holds at most 100 sources (`ABUSE_MAX_SUBJECTS`); the rest goes into part 2, sent at least 2 hours later, and at most 3 parts a day (decision D5). Past that, sources wait for the next day, newest first.
- **Freshness (7 days), per source.** At send time, an automatic digest keeps only the sources with activity in the last 7 days. Older sources stay in the draft, marked "older than 7 days", and go only with a send started by hand. A digest left with no fresh source is cancelled `too_old`, as today.
- **Pacing and caps:** unchanged in form. `daily_cap` now counts mails, so one digest is one. The 3 min spacing, the 1 h pause after a 4xx, the 3 deferrals, the no-retry on 5xx or unknown outcome all stay.
- **Reviewed digests:** a reviewed digest is frozen. New sources go into the next day's draft (so a recipient can have one reviewed digest and one draft).
- **Manual sends:** "Send now" or "Sent, next" works at any time on a draft or reviewed digest. It counts as the recipient's digest for the day: new sources wait for the next digest hour. A second manual send to the same recipient on the same day asks for confirmation ("This provider already got a report today").
- **Form-only and dead recipients:** no automatic digest. Form-only recipients go to the form queue (section 6). An `undeliverable` recipient waits for a new address.

### 5.2 Data model

| Change | Detail |
| --- | --- |
| `abuse_report_subjects.kind` | `attack_source`, `payload_host` or `c2`, backfilled from the report. The primary key becomes `(report_id, kind, subject_type, value)`, because one address can be both an attacker and a payload host |
| `abuse_reports.kind` | Keeps its column. New value `digest` for reports built by M38; old rows keep their kind |
| `abuse_reports.due_at`, `part` | When the digest is due (the digest hour of its day) and the part number |
| `abuse_reports.channel` | `mail` (default) or `form` (section 6) |
| Unique open draft | `ux_abuse_reports_open` becomes one `draft` per recipient (`WHERE status = 'draft'`), plus at most one `reviewed` per recipient |
| `report_smtp.digest_minute` | Minutes after 00:00 UTC, 0 to 1439, random on first save |
| `report_settings.digest_enabled` | Default true (decision D14) |
| `abuse_subject_outcomes (report_id, kind, subject_type, value, outcome, reply_id, at)` | Per-source outcome when a reply names some sources only (section 5.5) |

### 5.3 Worker changes

- `ingest/ingest/abuse/build.py`: groups by recipient only; keeps `kind` per subject; the size cap (250 KB) trims the oldest sources first into the next part.
- `ingest/ingest/reportmail/sender.py` `schedule()`: a digest is scheduled at `due_at` (not `now + hold`). The hold stays as a minimum delay after the last rebuild, so the owner can still look and cancel. Freshness is applied per source when the message is rendered for sending; the stored evidence keeps every source.
- One limit per recipient: a scheduling query refuses a second automatic mail to the same address in the same UTC day unless it is the next part of the same digest.

### 5.4 Migration from today's reports

1. The migration adds the columns, backfills `abuse_report_subjects.kind`, and keeps `ux_abuse_reports_open` until step 3.
2. Pending automatic send requests of drafts are cancelled with `digest_migration` (the owner sees them under Cancelled, with one sentence). Manual requests are kept.
3. On its first cycle, the new builder merges the open drafts of each recipient into one digest (all kinds), runs the guard on it, and marks the old drafts `superseded` (an existing status). Then the index changes.
4. Reviewed reports are not touched. They are sent as they are, as single-kind mails with the new XARF parts.
5. Sent and closed history is not changed. Results group old reports by their kind and digests by subject kind.

The upgrade is one-way at the data level; `just rollback` to v0.13 restores the database dump taken before the update, as for any migration.

### 5.5 Replies, tickets, bounces and form flags

A digest is one report with one reply token, one Message-ID and one set of subjects, so every existing match method works.

| Event | Effect |
| --- | --- |
| A reply to the digest (any method) | Outcome on the report, as today. Shown on every source of it |
| A verified reply that names some of the digest's sources in its own text (not in the quoted part) | Also an outcome on those sources only (`abuse_subject_outcomes`). Exact address or host match, case-insensitive, at most 100 names read. Unverified replies never set a per-source outcome |
| A reply that quotes a source's XARF `report_id` | New match method `xarf_id` (between `token` and `dsn`). It matches the report and the one source. Same trust rules as a token: verified only from a trusted sender |
| A ticket number | Linked to the report, and to the source when the same reply names exactly one source |
| A bounce | Whole digest (it did not arrive). Counts toward `undeliverable` once per mail, not once per source |
| A form-required reply | Whole recipient, as today |
| A takedown target | Per source, as today (`takedown_targets` are created per subject) |

### 5.6 UI

- **Reports list:** one row per digest: provider, mailbox, "12 sources (9 attack sources, 3 payload hosts)", due time ("goes at 07:42" or "waiting for tomorrow"), identity check, part number when there are parts.
- **Report page:** sources grouped by kind, each with its own outcome badge when it has one, and an "older than 7 days" mark when it will not go automatically. The Message card gets the XARF tab (section 4.5).
- **To send queue** (manual mode): one item per digest.
- **Settings > Sending:** "One mail per provider per day" (on), the digest hour, and an explanation of parts and caps.
- **Recipient panel:** "One mail per source (strict X-ARF)" switch, off by default, with a sentence on what it costs.

### 5.7 Docs

`docs/reporting.md` (sending and pacing), `docs/replies.md` (the `xarf_id` method and per-source outcomes), `docs/ui.md`, `docs/configuration.md`, `docs/api.md`, `docs/SECURITY.md` (the identity guard covers the XARF parts and their decoded evidence).

### 5.8 Privacy and security

- A digest names many sources at once. The guard runs on the whole mail, so one bad source blocks the whole digest; the page names the source to remove (or the owner discards it from the digest with one click).
- A digest gives one recipient a longer list of our sightings. It is the same data they would get in several mails.
- Fewer mails mean a lower risk of the sender's mailbox being flagged as bulk. The digest hour is random per install, so the network has no common send time.

### 5.9 Tests

- One digest per recipient per day, across kinds; parts above 100 sources, at most 3 a day, 2 h apart.
- Freshness per source at send time; empty digest cancelled `too_old`.
- Manual send counts for the day; second manual send needs the confirm flag in the API.
- Cap counts mails; spacing and deferrals unchanged (existing tests stay green).
- Migration: open drafts of one recipient merge into one digest; pending auto sends cancelled with `digest_migration`; reviewed reports untouched; upgrade test from a v0.13 dump.
- Replies: `xarf_id` match; per-source outcome only from verified replies naming the source in unquoted text; a bounce counts once.

### 5.10 Acceptance criteria

- With 30 sources spread over 3 kinds and one recipient, the node sends exactly one mail that day, at the digest hour, with one JSON per source.
- Upgrading the owner's node merges open drafts with no mail sent during the upgrade.
- Results, replies and takedowns keep working for old and new reports.

## 6. G4: the form queue

### 6.1 Which desks

A recipient goes to the form queue when one of these is true:

- a matched form-required reply marked it `form_only` (today's rule);
  A reply that accepts mail but suggests the form ("form preferred", rule `form-preferred`, migration `0042`) is an `auto_ack` and only sets `form_preferred`, a hint shown on the report page: it never routes to this queue. A form reply the owner links to a report by hand is read again by the outcome pass (`desk.learn_linked`).
- the shared directory (section 6.5) has an entry for it that says `accepts_mail: false` (decision D13). Such a recipient gets no mail at all, so no mail is wasted on a desk that ignores it;
- the owner switched it to form by hand.

### 6.2 Weekly grouping

Sources for a form-only recipient go into a `channel = 'form'` report per recipient and ISO week (Monday 00:00 UTC). It fills during the week like a digest. It appears in the queue as soon as it has a source, so the owner can submit early while the evidence is fresh; sources older than 7 days are marked, as in section 5.1.

### 6.3 The copy kit

The **To submit by form** tab (next to To send) lists the form reports, one card per provider and week. A card opens the kit:

| Field | Content | Notes |
| --- | --- | --- |
| Form | The form link, its host shown in text next to it | `rel="noopener noreferrer"`, `referrerpolicy="no-referrer"`, so the dashboard address never leaks in a `Referer` |
| Your email | The reply contact | Copy button |
| Your name | A new optional setting `form_name`, empty by default | Many forms require one; the owner chooses |
| Abuse type | The form's own label for our type, from the directory; else our words ("Login attack", "Exploit attempt", "Malware download") | |
| Addresses | One per line, or one block per address when the directory says `one_ip_per_submission` | Each block has its own copy button and a check box |
| First seen, last seen | UTC, with the report's precision | |
| Description | A short, factual text, already written, within the form's `max_chars` (default 1,000). Ends with `ref <token>` so a reply can match | Built from the same labels as the mail; the owner's intro is not used (it is often long) |
| Log excerpt | The first 20 evidence lines per source | |
| Evidence file | `evidence.csv`, or `evidence.txt` when the directory says the form takes text files only | Download button |

Every field and the file pass the identity guard, as a mail does. A blocked kit shows why and has no copy button.

A warning at the top of the kit, always: "The provider sees the address of the browser that submits the form. Open it through your VPN or the Tor Browser." Mail always leaves through the VPN; a form submitted from the owner's browser does not, unless the owner makes it.

**Submitted.** The button marks the report `sent` with `sent_via = 'form'` and the time. It counts as sent everywhere: the 14-day resend, takedown tracking, Results (a new channel "Form"), the effect measure. With per-address check boxes, the button is enabled once at least one is ticked, and only the ticked sources are marked sent; the others stay for next time. "Submitted" does not count against the SMTP daily cap.

### 6.4 Replies to form submissions

A form usually answers with a ticket mail to the reply contact. It matches by `ref <token>` when the desk quotes the description, by the sender's domain when exactly one recent report went there (form reports count as sent), or by ticket number. Nothing new is needed.

### 6.5 The shared directory of abuse forms

A data file, `reporting/forms/abuse-forms.yaml`, compiled to JSON and shipped in the ingest image with each release (decision D11), like bundled trap packs. It is data only: no template logic, no script, no HTML.

| Field | Bounds | Meaning |
| --- | --- | --- |
| `schema` | `suckerpot-abuse-forms/1` | |
| `id` | slug | Stable entry id |
| `provider` | 1 to 80 chars | Display name |
| `match.mailbox_domains` | 0 to 10 domains | Exact domain of the RDAP abuse mailbox |
| `match.asns` | 0 to 50 | ASNs of the provider |
| `official_domains` | 1 to 5 | The provider's own domains |
| `form_url` | `https`, host equal to or under one of `official_domains`, no IP literal, no user info, at most 300 chars, no query string except an allow-listed `lang` | |
| `accepts_mail` | `true`, `false` or `ignored` | `false` and `ignored` both send the recipient to the form queue |
| `xarf` | `unknown` (default), `accepted` or `strict` | Set only with a public source that says so |
| `one_ip_per_submission`, `file_types`, `max_chars` | | Kit hints |
| `fields` | 0 to 20 `{key, label, choices}` | The form's own labels; `key` is one of the kit fields; `choices` maps our types to the form's options |
| `source` | `https` URL | A public page of the provider that links to the form or describes its abuse process |
| `verified_on` | date | Last check by a maintainer |

Matching a recipient: exact mailbox domain first, then ASN of the subjects. CI validates the file (schema, bounds, URL rules) and warns on entries older than 365 days; the kit then says "last checked over a year ago".

**Where entries come from.** A node learns a form link from a verified reply on the provider's domain (today's rule). On the recipient panel, an administrator sees **Suggest for the shared directory**. It shows a short text to copy: provider name, mailbox domain, ASN, the form link, and "learned from a verified reply". It never contains an address we reported, a ticket number, the reply text or anything about the node. The owner posts it as an issue on the public repository. The panel warns that posting from a personal account links that account to reporting this provider (an anonymous path through the hub may come later, decision D12).

**Who reviews and how.** The repository's code owners review every change to `reporting/forms/` (a CODEOWNERS entry, like `traps/`). A form link from a reply is untrusted: it is a hint, never the proof. The reviewer:

1. opens the provider's official website (the domain in its RDAP record or its own site, not a link from the reply), through a VPN;
2. finds the abuse page there and checks that it links to the same form; that page becomes `source`;
3. reads the form without submitting it, and records the field labels and choices;
4. checks that the form host is under an official domain and that the link carries no tracking or session parameter;
5. sets `verified_on` and opens a pull request; CI must be green; another code owner approves when the author is a code owner.

In the dashboard, a directory link is labelled "From the shared directory, checked <date>". A link from a reply stays labelled "From a reply: check the address before you open it". When both exist and differ, both are shown with a warning.

### 6.6 Data model

- `abuse_reports.channel` (`mail` or `form`) and `week` (ISO week, form reports only).
- `abuse_recipients.form_source` (`reply`, `directory`, `manual`) and `form_entry` (directory id).
- `abuse_report_subjects.submitted_at` for per-address submissions.
- `report_settings.form_name`.

### 6.7 Worker and API

- `ingest/ingest/abuse/forms.py`: loads and validates the bundled directory at start; matches recipients; sets `form_only` with `form_source = 'directory'` (cleared when the entry goes).
- The builder routes form-only recipients to weekly form reports.
- API: `GET /abuse/forms` (the queue), `GET /abuse/reports/{id}/kit` (fields after the guard), `POST /abuse/reports/{id}/submitted` (with optional subject list; admin; asks nothing more than other sends).

### 6.8 Privacy and security

- The browser warning (section 6.3) is the main new risk: forms leave outside the VPN unless the owner takes care.
- The kit passes the identity guard field by field and as a whole.
- Links: never clickable unless `https` on an allowed host; shown with their host in text; no referrer.
- The directory is code-reviewed data in the release, covered by the release signature. A bad entry can at worst point the owner to a wrong page, which the host label and the review make unlikely. It cannot run anything.
- No automatic submission, no headless browser, no captcha solving (N1).

### 6.9 Tests

- Directory validator: URL rules (http, IP literal, foreign host, query string, user info all refused), bounds, schema.
- Recipient matching by mailbox domain and ASN; `accepts_mail: false` routes to the queue and blocks automatic mail.
- Weekly grouping; per-address submission marks only ticked sources.
- Kit fields pass the guard; a planted self term blocks the kit.
- The form link renders with `noreferrer` (component test) and is not a link when the host is not allowed.
- "Submitted" counts as sent in Results, resend and takedown tracking.

### 6.10 Acceptance criteria

- A form-only recipient never gets an automatic mail and appears in To submit by form with a complete kit.
- The directory ships in the release with at least the entries that the owner's past verified replies support, each reviewed as in section 6.5.
- An owner can go from the queue to a submitted report in under two minutes per provider, with every field one click away.

## 7. Security summary

| Asset | Threat | Defence |
| --- | --- | --- |
| The node's identity | A new field (XARF JSON, kit text) carries our address, a name or a project marker | `destination_ip` never set; tags from allow-lists only; no `honeypot` evidence source; the guard decodes MIME parts and evidence payloads; schema check before send |
| The owner's address | A form submitted from the home browser | A fixed warning in the kit; no automatic submission |
| The dashboard address | `Referer` when opening a form | `noreferrer` on every outgoing link |
| Third parties | Data sent beyond the recipient | XARF goes only to the abuse recipient; the directory and the effect measure send nothing; network sharing of the measure is opt-in and later (H2) |
| The owner's mailbox | Too many mails | One digest per recipient per day; cap counts mails; random digest hour |
| Honest numbers | An effect claimed without data | Minimum pairs, observation check, fixed wording, no percentage under the minimum |
| The directory | A malicious form link from a reply | Reply links are hints only; reviewers verify on the provider's own site; host shown in text; code owner review |

## 10. Decisions

The owner approved these on 2026-11-22.

| # | Topic | Decision |
| --- | --- | --- |
| D1 | XARF version | XARF v4 only (4.2.0). The v0.2 renderer goes. v0.2 is from about 2010, its schema host is gone, and v3 is archived in favour of v4 |
| D2 | Several sources in one mail | One complete v4 JSON per source in a `multipart/mixed` digest. A per-recipient "strict" switch (`xarf_strict`, off by default) sends one spec-shaped mail per source for desks known to need it |
| D3 | Kinds in one digest | One digest per recipient across all kinds, with a section per kind. The XARF type still says what each source did |
| D4 | Digest hour | A random minute per install between 06:00 and 09:00 UTC, editable in Settings > Sending |
| D5 | Big providers | Parts of at most 100 sources, at most 3 parts a day, at least 2 h apart. The rest waits for the next day, newest first |
| D6 | `evidence_source` and `confidence` | Both left out. `honeypot` would reveal us, and a neutral value would not be true |
| D7 | `reporter.org` default | The domain of the reply contact, with an optional `xarf_org` setting. No shipped phrase, because it would be searchable |
| D8 | Measure thresholds | N = 7 days (primary) and 30 days. A number is shown only with at least 30 observed pairs and 10 discordant pairs |
| D9 | Random holdout | Opt-in, off by default, at most 10 % of new candidates, held 21 days (`ABUSE_EFFECT_HOLDOUT_PCT`) |
| D10 | Network measure | v0.14 measures the hub's own reports only (H1). Pooling node reports (H2) comes later, opt-in, after a separate privacy review |
| D11 | Directory distribution | Shipped with releases only. The signed trap-pack channel can come later |
| D12 | Directory suggestions | Posted by hand as an issue in v0.14, with the warning on the recipient panel. An anonymous path through the hub needs a protocol change and may come later |
| D13 | Directory pre-flags form-only desks | Yes, for entries with `accepts_mail: false` and a public source. Such a recipient gets no mail |
| D14 | Digests on upgrade | On for every install, announced in the release notes, with a Settings switch to turn them off |
| D15 | Per-source outcomes from replies | Yes, from verified replies only, and only from their unquoted text |
| D16 | JSON transfer encoding | base64, as the spec says, with the guard decoding it |

No question is open.

## 11. What was checked, and what was not

Checked on 2026-11-22:

- xarf.org (overview, Email Transport, Common Fields, the connection, content and infrastructure type pages) and the `xarf/xarf-spec` repository: the version (4.2.0, released 2026-03-20), the required core fields, the 33 type schemas, the required fields of `login_attack`, `vulnerability_scan`, `sql_injection`, `malware` (`url` through `content-base`), `botnet` (`compromise_evidence`), and the licence (MIT).
- The archived `abusix/xarf` README (v3 is deprecated in favour of v4) and the AWS Abuse Signal docs (they validate v4 and convert v3).

Not checked:

- Which desks parse XARF automatically. No public page of Leaseweb, Hetzner, OVH or DigitalOcean that says so was found. The design therefore makes no claim about them; the directory's `xarf` field stays `unknown` until a public source says otherwise.
- The exact v0.2 mail header. The v0.2 specification could not be fetched. Some sources describe `X-XARF: PLAIN` for v0.2, while our code sends `X-ARF: YES`. The move to v4 makes this moot.
- How tolerant XARF parsers are of several JSON files in one `multipart/mixed` mail. The spec does not cover it (decision D2).
